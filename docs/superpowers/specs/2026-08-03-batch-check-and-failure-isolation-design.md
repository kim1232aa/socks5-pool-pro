# 批量检测与失败隔离设计

## 目标

- 候选池只放待检测节点。
- 管理员可随时启动一批待检测节点，多线程并发检测。
- 检测失败的节点从候选池移出，进入独立的失败栏。
- 来源再次刷新到同一个地址时，去重逻辑识别它已在失败栏，不放回候选池。
- 后台自动检测、来源刷新和周期任务都不得检测失败栏节点。
- 失败栏只能由管理员手动重新检测：
  - 成功 → 进转发池，从失败栏移除。
  - 再次失败 → 继续留失败栏。
- 失败节点不自动冷却恢复，不自动回候选池。
- 策略排除（如要求改IP不满足）归入失败栏，不回候选池。

## 状态与集合边界

系统对一个代理节点只保留一个主要归属：

```
来源刷新去重
  │
  ├─ 已在失败栏 ──► 只合并来源和最后发现时间，不进入候选池
  ├─ 已在转发池/资源索引 ──► 按现有去重逻辑处理
  └─ 全新节点 ──► 候选池（待检测）
                       │
                       ├── 检测成功 ──► 转发池
                       ├── 检测失败 ──► 失败栏
                       └── 策略排除 ──► 失败栏

失败栏
  │
  └── 管理员手动重测
        ├── 成功 ──► 转发池，从失败栏移除
        ├── 失败 ──► 更新失败信息，留在失败栏
        └── 策略排除 ──► 更新失败信息，留在失败栏
```

候选页只展示等待检测的节点。候选批量任务和来源自动检测在开始网络请求前，都必须通过 `CandidateCatalog` 原子领取节点并建立短暂租约；未取得租约的一方跳过该节点。检测中的节点仍属于候选集合，但不会被其他任务重复领取。任务异常中断且没有产生检测结果时，租约释放，节点仍是待检测候选，不得因为任务中断而误入失败栏。失败栏手动重测使用同类的失败记录租约，且这些租约永远不会被后台任务申请。

`CandidateCatalog` 现有的资源归属和去重记录可以继续保留在内部，但这些记录不属于候选池，也不由候选分页 API 返回。

## 失败栏实现

### 独立失败记录集合

在 `CandidateCatalog` 内增加与现有记录并列的失败记录集合。失败记录以现有规范化、protocol-aware 的代理 key 标识，至少保存：

- 完整代理声明（协议、地址和重测所需凭据）；
- 来源归属与最后发现时间；
- 失败类型：`unreachable` 或 `policy_filtered`；
- 最近错误摘要与最近检测时间。

失败记录必须包含独立重测所需的全部数据，不能依赖候选记录继续存在。候选分页与失败分页完全分离。

### 去重与来源合并

`begin()` 合并来源抓取结果时同时查询转发池/资源索引、候选记录和失败记录。来源再次抓到失败 key 时：

- 合并新的来源归属和最后发现时间到失败记录；
- 不创建候选记录；
- 不自动触发检测；
- 不改变该记录的失败类型和最近检测结果。

同一地址的不同协议继续使用不同 key，避免 HTTP 与 SOCKS 节点互相误判为重复。

### 检测结果发布

候选检测完成后，在一次目录更新中发布结果：

- `alive`：进入转发池，并从候选集合移除；
- `unreachable`：从候选集合移除，写入或更新失败记录；
- `policy_filtered`：从候选集合移除，写入或更新失败记录。

失败栏重测完成后：

- `alive`：进入转发池，并从失败集合移除；
- `unreachable` / `policy_filtered`：只更新失败类型、错误摘要和检测时间，记录继续留在失败集合。

目录更新遵循现有的 persist-then-publish 原子边界；过期任务结果不能覆盖更新后的目录快照。

### ResetHealthOutcomes

`ResetHealthOutcomes`（例如 `CheckURL` 变更后调用）不清除、不迁移失败记录。失败栏中的节点仍须管理员手动重测才能离开。该操作只重置仍属于候选池的检测元数据。

### 持久化与兼容

失败集合随候选目录一起持久化并在重启后恢复。缓存格式增加失败记录字段，读取旧格式时：

- 旧 `checked_failed` 记录迁移为 `unreachable` 失败记录；
- 旧 `policy_filtered` 记录迁移为 `policy_filtered` 失败记录；
- 其他现有资源归属记录按原语义恢复。

进程重启不会把失败记录恢复成候选。

## 管理员批量检测候选

### 启动与执行

新增一个短生命周期、内存态的候选检测任务：

- `POST /api/candidates/batch-check` 启动任务并返回 `202 Accepted`；
- 请求可选 `limit`，省略时使用现有 `MaxCandidates`，服务端将值限制在 `1..MaxCandidates`；
- 服务端从当前待检测候选中公平领取最多 `limit` 条，而不是要求浏览器传完整节点列表；
- 使用现有 `MaxConcurrent` 控制工作协程数量，使用现有 `CheckTimeout` 控制单节点检测超时；
- 检测复用正式代理验证链路，包括凭据探测、出口 IP、改 IP 策略、匿名性和地理信息；
- 同一时间只运行一个会修改候选/失败目录的人工检测任务；重复启动返回 `409 Conflict`；
- 人工检测任务与来源刷新在目录结果发布阶段串行化，避免同一节点被重复检测或由旧结果复活。

任务本身不持久化，也不提供暂停、恢复或队列。进程中断时，没有结果的候选仍留在候选池；已经原子发布的结果保持不变。

### 状态 API

- `GET /api/candidates/batch-check/status` 返回当前或最近一次任务状态；
- 最少包含 `state`、`total`、`completed`、`alive`、`failed`、`policyFiltered`、`startedAt` 和 `finishedAt`；
- 单节点错误写入失败记录，不因一个节点失败中止整批任务。

### 候选页

- 候选页只显示待检测节点，不再提供 `checked_failed` 或 `policy_filtered` 状态筛选；
- 增加“开始批量检测”按钮，默认按当前 `MaxCandidates` 启动；
- 运行期间轮询状态 API，展示进度和成功/失败计数，并禁用重复启动；
- 批次结束后刷新候选计数、失败计数和转发池计数。

管理员需要调整批量大小、并发数或超时时，继续使用现有的 `MaxCandidates`、`MaxConcurrent` 和 `CheckTimeout` 管理配置，不增加另一套任务专用配置。

## 独立失败栏与手动重测

### 失败分页 API

- `GET /api/failed-candidates` 使用独立计数和分页返回失败记录；
- 支持按来源、协议和失败类型过滤；
- 候选 API 不返回这些记录。

### 手动重测 API

- `POST /api/failed-candidates/retry`；
- 请求体为 `{"keys": ["socks5://1.2.3.4:1080", ...]}`；
- 只接受当前失败集合中存在的 key，不在失败栏的 key 返回明确的请求错误；
- 数量上限使用 `MaxCandidates`，并发和超时继续使用 `MaxConcurrent`、`CheckTimeout`；
- 与候选批量检测复用相同的验证器和人工任务互斥边界；
- 启动后返回 `202 Accepted`，进度由对应状态字段/API 提供；
- 成功节点进入转发池并从失败栏移除；失败或策略排除节点留在失败栏。

除这个管理员 API 外，任何来源刷新、周期任务、健康检查或启动恢复流程都不得领取失败记录。

### 管理后台

- 在资源管理导航中增加独立“失败节点”页签，并显示独立数量；
- 页面提供失败类型、来源和协议筛选、分页与多选；
- 仅在失败页提供“重新检测”操作；
- 重测期间展示任务进度并禁用重复提交；
- 候选页与失败页不通过状态筛选复用同一列表，避免后台行为再次混淆。

## 来源刷新后的自动检测

来源刷新继续使用现有并发验证链路和 `MaxCandidates` 采样：

1. `begin()` 合并来源结果，同时阻止失败记录重新进入候选；
2. 本轮被选中的候选使用 `MaxConcurrent` 并发检测；
3. `alive` 进入转发池；
4. `unreachable` 和 `policyFiltered` 从候选移入失败栏；
5. 超出本轮检测上限、尚未被领取的节点继续作为待检测候选；
6. 来源抓取本身失败不等于节点检测失败，不把未检测节点移入失败栏。

后台周期刷新只处理本轮新候选和候选池中的待检测节点，永远不扫描失败集合。

## 不做的事

- 不把失败栏实现成候选状态筛选；
- 不为候选池增加新的失败状态；失败类型只保存在失败记录中；
- 不增加自动冷却、自动重测或自动回候选池；
- 不让后台周期任务检测失败栏；
- 不持久化人工任务进度，不增加暂停、恢复或任务队列；
- 不改动转发池节点的现有 health recheck 逻辑；
- 不增加新的并发、超时或批量大小配置项。

## 测试与验收

### 目录与持久化

- 候选检测成功后进入转发池，并从候选分页消失；
- 候选检测失败或策略排除后从候选分页消失，并出现在失败分页；
- 失败记录保存完整代理数据，可以在候选记录不存在时独立重测；
- 候选分页和失败分页的计数、筛选及数据完全隔离；
- 来源再次抓到失败节点时只更新来源元数据，不重新创建候选；
- protocol-aware key 不会把不同协议的相同地址错误去重；
- `ResetHealthOutcomes` 不清除失败记录；
- 失败记录持久化后可在重启恢复，且不会恢复成候选；
- 旧缓存中的 `checked_failed` / `policy_filtered` 可正确迁移。

### 批量任务

- 候选批量任务最多领取 `limit` 条，并受 `MaxCandidates` 限制；
- 实际并发不超过 `MaxConcurrent`，单节点检测遵守 `CheckTimeout`；
- 同一节点不会被人工任务和来源刷新重复发布结果；
- 一个节点失败不会中断其余节点；
- 重复启动人工任务返回 `409`；
- 任务异常中断时，无检测结果的候选仍留在候选池。

### 失败栏重测

- 重测 API 拒绝不在失败栏中的 key；
- 重测成功进入转发池并从失败栏消失；
- 重测失败或策略排除继续留在失败栏，并更新最近结果；
- 自动刷新、定时任务和启动恢复均不会领取失败记录。

### 管理后台

- 候选页只能看到待检测节点并能启动批量检测；
- 失败节点有独立页签、计数、分页、筛选和手动重测操作；
- 两类人工任务都能显示进度，运行期间不能重复启动；
- 任务结束后候选、失败和转发池数量同步刷新。
